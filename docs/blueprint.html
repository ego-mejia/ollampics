Ollympics

Sistema de benchmarking agéntico para modelos locales en Ollama. Cada modelo compite en todas las pruebas, registra sus estadísticas en SQLite, y el dashboard React permite comparar modelos, cuantizaciones, y configuraciones de runtime.

Visión general

Ollympics responde una pregunta concreta: "¿qué modelo local me conviene correr en mi máquina, para qué tarea, y con qué configuración?". El sistema no es un duelo en vivo entre modelos — es un decatlón donde cada modelo participa independientemente, registra su desempeño en cada prueba, y la comparación ocurre después en el dashboard.

El uso típico es: el usuario tiene varios modelos descargados en Ollama (distintas familias, tamaños, cuantizaciones). Dispara una corrida especificando qué modelos quiere evaluar y qué suites correr. El sistema levanta cada modelo en Ollama, ejecuta las suites no completadas, guarda métricas detalladas, y avanza al siguiente modelo. El usuario abre el frontend para explorar el ranking, comparar dos modelos lado a lado, y entender en qué tarea cada uno brilla o falla.

Filosofía

Cada modelo corre solo, en serie. La VRAM unificada de un Apple Silicon (o la GPU única de la mayoría de máquinas) no permite correr modelos en paralelo sin que las mediciones se contaminen. El paralelismo de Ollympics ocurre en el dashboard, no en el runner.

Principios de diseño

PrincipioConsecuencia práctica
Determinismo primerotemperature=0, seed=42, top_p=1 por default. Reproducibilidad > variedad.
IdempotenciaRe-ejecutar el mismo benchmark no recalcula tareas ya completadas. La clave única es (modelo, runtime_hash, task_id, task_version).
Atribución limpiaTres ejes ortogonales: modelo, runtime, tarea. Cada variable cambia por separado para que la comparación sea legible.
Veredictos auditablesCada intento guarda el transcript completo (prompt + respuesta + tool calls). Sin transcript no hay forma de revisar por qué algo falló.
Local-firstEl sistema funciona sin red. La API externa (DeepSeek como juez) es opt-in por suite.
Versionado de tareasCada task tiene task_id + version. Si modificas un test, las corridas viejas siguen siendo válidas; las nuevas se recalculan automáticamente.
Tareas como datosLas tasks se definen en YAML, no en código. Agregar una task no requiere cambiar el runner.

Flujo de una corrida

  1. Usuario dispara oly run --models qwen3.6:27b-mlx,gemma4:12b-mlx --suites all (o lo mismo desde el frontend).
  2. El runner crea una fila en runs con la configuración (modelos, runtime, suites, git_sha del harness).
  3. Para cada modelo: pull si falta, set env de KV cache, levantar en Ollama, warmup prompt.
  4. Para cada suite y cada task: chequear si ya existe attempt válido para (modelo, runtime_hash, task_id, task_version). Si sí, skip.
  5. Ejecutar con N tries (configurable por task). Medir tokens/s, ttft, vram, watts. Guardar attempt completo.
  6. Si la suite usa juez DeepSeek, mandar transcript a DeepSeek tras cada attempt y guardar veredicto.
  7. Emitir evento por WebSocket al frontend en cada hito (task started, attempt finished, suite finished, model finished).
  8. Al terminar el modelo: ollama stop para liberar VRAM antes de cargar el siguiente.

Schema de base de datos

SQLite con cuatro tablas principales más un par auxiliares. Pensado para que las queries del dashboard sean simples y rápidas.

-- Configuración de una corrida. Una corrida puede abarcar múltiples modelos y suites.
CREATE TABLE runs (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  status          TEXT NOT NULL,              -- queued | running | done | failed | cancelled
  harness_sha     TEXT NOT NULL,              -- git sha del harness al momento de la corrida
  config_json     TEXT NOT NULL,              -- snapshot completo de la config (modelos, suites, params)
  notes           TEXT
);

-- Catálogo de modelos vistos. Se llena automáticamente al evaluar.
CREATE TABLE models (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  name            TEXT NOT NULL,              -- ej. "qwen3.6:27b-mlx"
  family          TEXT,                       -- ej. "qwen3.6"
  size_params_b   REAL,                       -- ej. 27.0 (en miles de millones)
  quantization    TEXT,                       -- ej. "mlx-q4", "Q5_K_M", "Q8_0"
  backend         TEXT,                       -- "mlx" | "gguf"
  size_bytes      INTEGER,
  UNIQUE(name)
);

-- Combinación específica de runtime params que aplica a un intento.
-- Tener esto separado permite comparar "mismo modelo, distinto KV cache".
CREATE TABLE runtime_configs (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  hash            TEXT NOT NULL UNIQUE,       -- hash determinista de los campos
  num_ctx         INTEGER NOT NULL,           -- ej. 8192, 32768
  kv_cache_type   TEXT NOT NULL,              -- "f16" | "q8_0" | "q4_0"
  num_gpu         INTEGER,
  num_thread      INTEGER,
  temperature     REAL NOT NULL DEFAULT 0.0,
  seed            INTEGER NOT NULL DEFAULT 42,
  extra_json      TEXT                        -- otros params específicos
);

-- Catálogo de tasks que existen, con versión.
CREATE TABLE tasks_registry (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id         TEXT NOT NULL,              -- ej. "baseline.json_simple"
  version         INTEGER NOT NULL,           -- bump cuando cambia el contrato del test
  suite           TEXT NOT NULL,              -- "baseline" | "tool_calling" | "rag" | ...
  spec_json       TEXT NOT NULL,              -- definición completa
  judge_required  BOOLEAN NOT NULL DEFAULT 0, -- si necesita LLM judge
  UNIQUE(task_id, version)
);

-- Cada intento de ejecutar una task con una configuración específica.
CREATE TABLE attempts (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id          INTEGER NOT NULL REFERENCES runs(id),
  model_id        INTEGER NOT NULL REFERENCES models(id),
  runtime_id      INTEGER NOT NULL REFERENCES runtime_configs(id),
  task_id         INTEGER NOT NULL REFERENCES tasks_registry(id),
  try_n           INTEGER NOT NULL,           -- 1..N
  status          TEXT NOT NULL,              -- success | fail | error | timeout
  started_at      TIMESTAMP NOT NULL,
  finished_at     TIMESTAMP,
  wall_time_s     REAL,
  ttft_ms         INTEGER,                    -- time to first token
  tokens_in       INTEGER,
  tokens_out      INTEGER,
  tps_decode      REAL,                       -- tokens/s en fase de decode
  peak_vram_mb    INTEGER,
  avg_watts       REAL,
  error_type      TEXT,                       -- json_invalid | timeout | wrong_answer | loop | api_error
  error_message   TEXT,
  transcript_json TEXT NOT NULL,              -- prompts, respuestas, tool calls completos
  UNIQUE(run_id, model_id, runtime_id, task_id, try_n)
);

-- Veredictos de jueces (DeepSeek u otros) sobre attempts que requieren evaluación abierta.
CREATE TABLE judge_evaluations (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  attempt_id      INTEGER NOT NULL REFERENCES attempts(id) ON DELETE CASCADE,
  judge_model     TEXT NOT NULL,              -- ej. "deepseek-chat"
  rubric_name     TEXT NOT NULL,              -- ej. "rag_open_answer_v1"
  score           REAL NOT NULL,              -- 0.0 - 1.0
  pass            BOOLEAN NOT NULL,
  rationale       TEXT,
  cost_usd        REAL,
  created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(attempt_id, judge_model, rubric_name)
);

-- Índices clave para las queries del dashboard.
CREATE INDEX idx_attempts_model_task ON attempts(model_id, task_id);
CREATE INDEX idx_attempts_run ON attempts(run_id);
CREATE INDEX idx_attempts_status ON attempts(status);
¿Por qué runtime_configs separado?

Si quieres comparar "qwen3.6:27b-mlx con KV cache f16" vs "qwen3.6:27b-mlx con KV cache q8_0", ambos comparten model_id pero difieren en runtime_id. La query del dashboard se vuelve trivial: WHERE model_id=X GROUP BY runtime_id. Si hubiéramos metido el runtime dentro de attempts, las queries de comparación serían un dolor.

Vistas materializadas (para el dashboard)

-- Mejor attempt por (modelo, runtime, task): el primer success o el último error si nunca pasó.
CREATE VIEW best_attempts AS
SELECT a.* FROM attempts a
WHERE a.id = (
  SELECT id FROM attempts a2
  WHERE a2.model_id = a.model_id
    AND a2.runtime_id = a.runtime_id
    AND a2.task_id = a.task_id
  ORDER BY (a2.status = 'success') DESC, a2.try_n ASC
  LIMIT 1
);

-- Resumen por modelo y suite.
CREATE VIEW model_suite_summary AS
SELECT
  m.name AS model_name,
  rc.hash AS runtime_hash,
  tr.suite AS suite,
  COUNT(*) AS total_tasks,
  SUM(CASE WHEN ba.status='success' THEN 1 ELSE 0 END) AS successes,
  AVG(ba.tps_decode) AS avg_tps,
  AVG(ba.ttft_ms) AS avg_ttft_ms,
  AVG(ba.try_n) AS avg_tries
FROM best_attempts ba
JOIN models m ON m.id = ba.model_id
JOIN runtime_configs rc ON rc.id = ba.runtime_id
JOIN tasks_registry tr ON tr.id = ba.task_id
GROUP BY m.id, rc.id, tr.suite;

Loop principal del runner

El runner es el corazón de Ollympics. Vive en backend/core/runner.py y se ejecuta como tarea asyncio que el endpoint POST /api/runs dispara.

async def execute_run(run_id: int):
    run = await db.get_run(run_id)
    await emit("run.started", run_id=run_id, ...)
    try:
        for model_spec in run.config.models:
            await prepare_model(model_spec)            # pull + set env + warmup
            await emit("model.started", model=model_spec.name)
            for runtime in run.config.runtime_configs:
                await ollama.configure_runtime(runtime)
                for suite_name in run.config.suites:
                    suite = registry.get_suite(suite_name)
                    for task in suite.tasks:
                        if await db.already_completed(model_spec, runtime, task):
                            continue
                        await run_task_with_retries(
                            run_id, model_spec, runtime, task, n=task.max_tries
                        )
                        if run.cancel_requested:
                            return
            await ollama.stop(model_spec.name)         # liberar VRAM
            await emit("model.finished", model=model_spec.name)
    finally:
        await db.mark_run_done(run_id)
        await emit("run.finished", run_id=run_id)


async def run_task_with_retries(run_id, model, runtime, task, n):
    for try_n in range(1, n + 1):
        attempt = await execute_task(run_id, model, runtime, task, try_n)
        if attempt.status == "success":
            break

Control de Ollama

Ollama se controla via su HTTP API en localhost:11434 y vía subprocess para comandos de lifecycle (pull, list, ps, stop).

Parámetros de runtime que importan

ParámetroCómo se configuraPor qué importa
num_ctxopción del requestTamaño de ventana de contexto. Cuantizaciones bajas degradan con contexto grande.
kv_cache_typeenv OLLAMA_KV_CACHE_TYPEf16 / q8_0 / q4_0. Reducir VRAM a costa de calidad.
flash_attentionenv OLLAMA_FLASH_ATTENTIONRequerido para KV cache cuantizado.
num_gpuopción del requestCuántas capas a GPU; en Apple Silicon es siempre todas.
temperature, seed, top_popciones del requestDeterminismo: temp=0, seed=42.
KV cache cuantizado en Ollama

Para usar q8_0 o q4_0 en KV cache, hay que levantar Ollama con ambas envs: OLLAMA_FLASH_ATTENTION=1 y OLLAMA_KV_CACHE_TYPE=q8_0. Como Ollama lee estas envs al arrancar el server, cambiar el KV cache implica reiniciar el server. El runner lo maneja: si la siguiente runtime_config requiere distinto KV cache, mata Ollama, re-exporta envs, lo vuelve a levantar, y reanuda.

Medición de VRAM en Apple Silicon

No hay nvidia-smi. Las fuentes que sí funcionan:

  • ollama ps: muestra modelos cargados y memoria que reportan ocupar. Rápido, suficiente para "peak VRAM" aproximado.
  • sudo powermetrics --samplers gpu_power -n 1 -i 100: potencia instantánea en watts. Requiere sudo. Lo corremos como un proceso que muestrea durante el attempt.
  • ioreg -r -c IOAccelerator: memoria GPU total y allocada (sin sudo). Útil como backup.

Sistema de métricas

MétricaDefiniciónCaptura
ttft_msTime to first token: ms desde envío del request hasta primer chunk de respuesta.Cronómetro alrededor del primer evento de stream.
tps_decodeTokens/s durante decode (excluye prefill).tokens_out / (wall_time - ttft).
wall_time_sTiempo total extremo a extremo de un attempt.Cronómetro alrededor del loop completo del attempt.
tokens_in / tokens_outReportados por Ollama en el último chunk del stream.Parsea prompt_eval_count y eval_count.
peak_vram_mbVRAM máxima ocupada por el modelo durante el attempt.Sampler que llama ollama ps cada 250ms.
avg_wattsPotencia GPU promedio durante el attempt.Sampler de powermetrics en background.
n_tries_usedCuántos intentos hicieron falta para éxito.Contador en run_task_with_retries.
tool_call_format_errorsCantidad de tool calls con JSON inválido o nombre desconocido en el attempt.El parser de tools cuenta y reporta.
successBooleano. Lo define el verificador determinista o el juez según la task.Por task (ver Formato de tasks).

Métrica derivada: agentic_efficiency

agentic_efficiency = success_rate × (tps_decode / avg_tries_used)

Captura que un modelo rápido pero inconsistente puede ser peor que uno lento pero acertado. Se calcula en la vista, no se guarda.

Sistema de juez

Híbrido por filosofía. Cada task declara su modo de evaluación:

ModoCuándo usar
exact_matchFactoides con respuesta canónica (single string o set).
regexRespuesta debe matchear patrón (ej. "número entre tags").
json_schemaRespuesta debe ser JSON válido contra schema declarado.
tool_traceVerifica secuencia de tool calls esperada con argumentos válidos.
code_execEjecuta código devuelto y compara contra casos de prueba.
llm_judgeUsa DeepSeek con una rúbrica para evaluar respuesta abierta. Único modo que requiere red.
compositeCombinación: varios verificadores cuyo AND/OR define success.

Juez LLM con DeepSeek

Para preguntas abiertas (RAG hard, calidad de plan, coherencia de Personal Agent), se manda al juez:

system_prompt = """Eres un juez evaluador estricto. Lees un transcript de
modelo y aplicas la rúbrica dada. Respondes SOLO con JSON:
{"score": 0.0-1.0, "pass": bool, "rationale": "..."}
No agregues nada más."""

user_prompt = f"""
TASK: {task.description}
GROUND TRUTH: {task.expected}
RUBRIC: {rubric.criteria}
TRANSCRIPT: {attempt.transcript}
"""

El veredicto se persiste en judge_evaluations junto con el costo en USD. Si se vuelve a evaluar el mismo attempt con la misma rúbrica, devuelve el cache.

Suite 1 · Baseline

Propósito

Sanity check rápido. Descarta modelos rotos antes de invertir tiempo en suites largas. ~2 min por modelo.

Tasks (5)

  • baseline.short_generation: completar una oración. Veredicto: regex.
  • baseline.json_simple: devolver JSON con 3 campos pedidos. Veredicto: json_schema.
  • baseline.factual_qa: pregunta factual simple. Veredicto: exact_match.
  • baseline.instruction_following: instrucción con 3 reglas (lista numerada, en español, sin emojis). Veredicto: composite de 3 regex.
  • baseline.refusal: pregunta ambigua mal-formada. Veredicto: llm_judge con rúbrica "pide clarificación en lugar de inventar".

Métricas clave

success_rate, tps_decode, ttft_ms.

Suite 2 · Tool Calling Fidelity

Propósito

Capacidad fundamental para flujos agénticos. Si esto falla, todo lo demás falla.

Setup

Catálogo de 6 tools mockeadas con respuestas deterministas: get_weather, search_web, send_email, calculator, read_file, create_calendar_event.

Tasks (8)

  • tools.single_call_simple: prompt requiere 1 tool call obvia.
  • tools.single_call_arg_typing: prompt requiere tool con argumentos de tipos específicos (int, ISO date, enum).
  • tools.no_call_needed: prompt NO necesita tools. Mide false-positive rate.
  • tools.sequential_2: 2 tools en secuencia, output de la 1ra alimenta la 2da.
  • tools.sequential_3: 3 tools en cadena.
  • tools.error_recovery: 1ra tool devuelve error simulado; debe reintentar con args distintos.
  • tools.parallel_independent: prompt pide 2 cosas independientes — debería llamar ambas en paralelo (si el modelo lo soporta).
  • tools.ambiguous_no_clarify: tool call que requiere info que el usuario no dio. Debe pedir clarificación, no inventar.

Verificadores

Todos tool_trace. Comparan secuencia esperada de (tool_name, args_schema) contra lo emitido. Cuentan errores de JSON inválido por separado.

Suite 3 · RAG

Propósito

Capacidad de responder usando contexto recuperado, distinguir entre "está en el corpus" y "no está", y no contradecir lo recuperado.

Setup

  • Corpus: documentos ficticios de una empresa imaginaria Helion Robotics (ver sección Corpus RAG).
  • Vector store: ChromaDB local en data/chroma/.
  • Embedder: nomic-embed-text via Ollama. Cargado en paralelo al modelo bajo evaluación.
  • Top-k: 4 chunks por query. Tamaño de chunk: ~500 tokens con overlap de 50.

Q&A: 50 preguntas estratificadas

TierNTipoVerificador
factual_single_doc20Respuesta literal en un chunk.exact_match (fuzzy)
multi_doc_synthesis20Requiere unir 2-3 chunks.llm_judge con rúbrica "menciona los N hechos clave"
out_of_corpus10Respuesta NO está en el corpus. Test de honestidad.llm_judge con rúbrica "modelo dice no saber, no inventa"

Métricas separadas

  • retrieval_recall@4: ¿el chunk correcto entró al contexto? (Anotado en el ground truth de cada Q&A.) No mide el modelo, mide al embedder.
  • answer_quality: el verificador anterior. Mide al modelo dado contexto correcto.
  • faithfulness: ¿la respuesta contradice lo recuperado? (Juez con rúbrica de fidelidad.)
  • hallucination_on_oop: en preguntas out-of-corpus, % de veces que el modelo inventa una respuesta vs admite no saber.

Suite 4 · Planning + Execution

Propósito

Distinguir dos capacidades que suelen confundirse: planear vs ejecutar. Construido con LangGraph.

Sub-modalidad 4a · Plan propio

El modelo recibe el problema, debe producir un plan estructurado, y luego ejecutarlo (paso a paso, mismo modelo).

Sub-modalidad 4b · Plan dado

El modelo recibe el problema + un plan canónico pre-generado por Claude. Solo ejecuta los pasos. Aísla capacidad de ejecución.

El insight

Comparar 4a vs 4b para el mismo modelo y misma task te dice cuánto del fracaso vino de no saber planear vs no saber ejecutar. Modelos chicos a menudo pueden ejecutar bien si reciben un buen plan — esto te lo confirma con datos.

Tasks (10)

  • planning.refactor_function: refactorizar un snippet siguiendo plan de pasos.
  • planning.web_research: investigar tema con tool calls (mockeadas) y producir resumen estructurado.
  • planning.data_pipeline: dada una tabla CSV, ejecutar transformaciones específicas.
  • planning.bug_fix_localization: dado un bug report y código, identificar línea problemática.
  • planning.api_design: diseñar endpoints REST para un caso de uso descrito.
  • ... + 5 más cubriendo distintas variedades.

Verificador

composite con piezas deterministas (¿produjo plan en formato esperado? ¿llamó las tools esperadas?) + llm_judge con rúbrica de calidad sobre el resultado final.

Suite 5 · Multi-agent (research)

Propósito

Cómo se comporta el modelo en un workflow multi-rol realista. Único lugar donde usamos CrewAI: la suite incluye el overhead del framework a propósito, porque es parte del costo real de este patrón.

Setup

Crew de 3 agentes (mismo modelo en los tres roles):

  • Researcher: investiga un tema usando tools (mockeadas: search, fetch_doc).
  • Critic: revisa el output del researcher, marca gaps.
  • Writer: produce el reporte final integrando feedback.

Tasks (4)

  • multi.research_short: tema acotado, ~3 rondas esperadas.
  • multi.research_deep: tema complejo, 5+ rondas.
  • multi.research_contradiction: docs con info contradictoria, requiere reconciliación.
  • multi.research_blocked: tool falla intermitentemente, mide resiliencia del crew.

Métricas

llm_judge con rúbrica de calidad del reporte final + medición de overhead: tokens totales gastados, número de mensajes entre agentes, % de mensajes que fueron "redundantes" según el juez.

Suite 6 · Personal Agent

Propósito

La suite que mejor refleja "¿este modelo serviría como mi asistente diario?". 20 turnos de conversación con tool use y recall probes.

Setup

  • Conversación de 20 turnos. El "usuario" es simulado por DeepSeek siguiendo un guion semi-estructurado.
  • 5 tool calls esperadas, una cada ~4 turnos.
  • Tools disponibles: get_weather, search_web, add_to_calendar, set_reminder, take_note.
  • System prompt fijo: asistente personal con persona definida.

Estructura del guion

turno 1 (user):  saludo + presentación con un hecho clave plantado
                 ("hola, soy Eduardo, vivo en Querétaro")
turno 2 (user):  pregunta casual (mide ttft + naturalidad)
turno 3 (user):  pide una tool (set_reminder con info que se requerirá después)
turno 4-5:       conversación libre, otro hecho plantado
turno 6:         pide otra tool (get_weather)
turno 7-8:       conversación, plantar tercer hecho
turno 9:         pide tool (add_to_calendar)
turno 10:        ★ recall probe 1 — "¿en qué ciudad vivo?"
turno 11-12:     conversación
turno 13:        pide tool (search_web con argumentos derivados del contexto previo)
turno 14:        ★ recall probe 2 — referencia indirecta a algo dicho en turno 7
turno 15-17:     conversación con cambio de tema
turno 18:        pide tool (take_note pidiendo recuperar algo recordado)
turno 19:        ★ recall probe 3 — preguntar sobre el reminder del turno 3
turno 20:        cierre con resumen pedido (¿qué hicimos hoy?)

Métricas

  • recall@N_turns: % de recall probes contestadas correctamente. 3 probes en este guion.
  • tool_fidelity_in_context: misma medición que Suite 2 pero con historia larga acumulada.
  • persona_consistency: llm_judge evalúa si el modelo mantiene la persona del system prompt sin contradecirse.
  • ttft_drift: comparar ttft_ms turno 2 vs turno 18. Mide degradación con contexto creciente.
  • tps_drift: análogo para tps_decode.
  • closing_recall: el resumen del turno 20 — ¿menciona N de los hitos clave?

Por qué importa el simulador de usuario

Si el script fuera 100% determinista, el modelo podría aprender el patrón. Usar DeepSeek como simulador introduce variabilidad realista pero respeta los hitos obligatorios. El simulador tiene su propio guion con instrucciones tipo: "en el turno 10, sin importar lo que el modelo haya dicho antes, pregunta en qué ciudad vives".

Decisiones de diseño

¿Por qué no correr modelos en paralelo?

La VRAM unificada de Apple Silicon (y la VRAM dedicada de la mayoría de GPUs) no permite cargar múltiples modelos grandes sin que peleen por recursos. Aún si caben, las mediciones de tps se contaminan porque comparten ancho de banda de memoria. La serialidad es una feature, no un bug. El paralelismo de Ollympics está en el dashboard: una corrida puede tomar horas, pero el análisis después es instantáneo.

¿Por qué SQLite y no Postgres desde el día 1?

Para un usuario único, una máquina, datos en MB-bajos GB: SQLite es perfecto. Cero ops, cero containers, archivos fáciles de backup. Migración a Postgres es trivial con SQLAlchemy si crece (ej. para reportar resultados desde varias máquinas a un dashboard centralizado).

¿Por qué LangGraph + CrewAI en lugar de uno solo?

LangGraph es más declarativo y permite mediciones limpias (cada nodo del grafo es una unidad medible). CrewAI introduce su propio prompting y reglas internas que son parte del costo real del patrón multi-rol. Queremos medir ambos: "cómo se comporta este modelo en un grafo controlado" (LangGraph, suite Planning + Personal Agent) y "cómo se comporta en un workflow multi-rol idiomático" (CrewAI, suite Research). Conclusiones distintas, ambas válidas.

¿Por qué un corpus RAG ficticio en lugar de uno real?

Si usamos docs reales (ej. docs de FastAPI), el modelo probablemente las vio durante pre-training. La señal del RAG se contamina: el modelo puede contestar bien sin haber leído el contexto recuperado. Un corpus ficticio nos garantiza que la respuesta correcta SOLO puede venir del retrieval — lo cual aísla la capacidad RAG.

¿Por qué un juez externo (DeepSeek) y no un modelo local?

Usar otro modelo local como juez sesga las evaluaciones a favor de modelos similares al juez. Un modelo externo fuerte (DeepSeek-V3 o GPT-4 o Claude) sirve como árbitro neutral. DeepSeek se eligió por costo bajo y calidad alta. El juez es opt-in por task: tareas con verificador determinista NO llaman al juez.

¿Por qué versionar las tasks?

Cualquier cambio sustantivo en un verificador, prompt o ground truth invalida los resultados anteriores. Si task_id queda igual pero version cambia, los attempts viejos siguen siendo válidos en su versión, y los nuevos se recalculan automáticamente. Sin esto, modificar un test corrompería tu histórico silenciosamente.

¿Por qué warmup obligatorio?

La primera inferencia tras cargar el modelo es órdenes de magnitud más lenta (carga a VRAM, compilación de kernels). Esa medición contamina cualquier promedio. Un warmup descartable de 1 prompt corto resuelve el problema y refleja el escenario real (un usuario real interactúa con un modelo ya cargado).

Preguntas abiertas

Cosas que vale la pena decidir cuando lleguemos a implementar la fase correspondiente:

  • Streaming en el frontend: ¿queremos ver los tokens fluir en vivo durante /runs/:id/live, o solo el progreso por attempt? Streaming es bonito pero agrega complejidad en el WS.
  • Almacenamiento de transcripts: los transcripts pueden ser largos (~50KB cada uno en Personal Agent). En SQLite caben sin drama, pero podemos comprimir con zstd a futuro.
  • Comparación A vs B vs C: el endpoint /api/compare arranca soportando 2; ¿lo extendemos a N modelos en el v1 del frontend o esperamos a v2?
  • Costo de DeepSeek: ¿queremos un budget cap por corrida que detenga el uso del juez si se pasa? Probablemente sí — implementación simple en core/judge.py.
  • Multi-host: si en el futuro queremos correr bench en otra máquina y reportar al mismo dashboard, ¿migramos a Postgres + API auth, o un sync de SQLite es suficiente?
